## 三、发现的关键技术问题（真实记录）

### 3.1 上游缺陷：`runner_status` 状态同步滞后（已修复）

两平台均已 `completed=true`、`progress=100%` 时，`runner_status` 仍长期停留在 `"running"`，
导致轮询脚本空转 20 分钟以上。

- **修复**：`wait_simulation()` 增加完成判定条件 —— `twitter_completed && reddit_completed && progress>=100`；
- 并增加 `max_wait` 超时保护。
- 该问题不产生额外费用，但会浪费等待时间。

### 3.2 方法学修正：1 轮 = **60 分钟**，不是 2 小时

早期脚本写死「1 轮 ≈ 2 小时」，与真实不符。
实测 `simulation_config.json`：`time_config.minutes_per_round = 60`、`total_simulation_hours = 72`。

- **修复**：`compute_metrics.py` 新增 `--minutes-per-round`（默认 60），达峰时间按真实配置换算；
- 绘图脚本 x 轴标签同步改为「时间尺度见各实验 time_config.minutes_per_round」。

### 3.3 重要机制发现：`event_config` 原生支持内容注入

`simulation_config.json` 中存在两个关键字段：

- **`initial_posts`**（本次 6 条）：初始谣言/反驳内容由 LLM 自动生成并注入；
- **`scheduled_events`**（本次为 `None`，符合无干预基线预期）：**定时事件注入入口**。

> **对实验的意义**：实验二（辟谣时点）与实验三（辟谣形态）具备**原生注入通道**，
> 无需再用「提前终止 + 二段运行」的近似方案。建议正式实验优先走 `scheduled_events`。

### 3.4 实验设计警告：基线组已被 LLM 自动掺入辟谣内容

本次 requirement 明确声明「全程不注入任何官方辟谣信息」，但 LLM 生成的 `initial_posts` 中
仍包含「这个视频明显是AI合成的，大家别传了！等官方通报吧。」等反驳性内容。

> **风险**：无干预基线被污染，会削弱与干预组的对照差异。
> **对策**：正式实验必须在 requirement 中显式约束初始内容立场，并在跑后校验 `initial_posts`。

### 3.5 客户端 Bug：multipart 字段名错误（已修复）

上传接口字段名必须是 `files`（源码 `request.files.getlist('files')`），
早期脚本用自定义 key 会导致 400。已修复。

### 3.6 绘图脚本曾可产出空图（已修复）

因 3.1 导致提前中断时，`plot_fig_4_1_4_2.py` 在所有实验组缺失的情况下仍会保存空白图，
违反「不得用空白图表冒充正式成果」。已加入守卫：有效组 < 2 时拒绝出图。
**本次产生的空图已删除**，当前 `deliverables/figures/` 下无 4-1 / 4-2 文件。

### 4.3 正式六组实验成本估算

以本次实测为基准（「3 Agent × 2 轮 + 全部一次性开销」≈ ¥0.03）：

| 场景 | Agent 数 | 轮数 | 单组估算 | 6 组合计 |
|---|---|---|---|---|
| 保守（维持微种子规模） | ~5 | 15 | ¥0.05–0.15 | **¥0.3–0.9** |
| 推荐（完整种子，约 30 Agent） | ~30 | 15 | ¥0.3–0.8 | **¥2–5** |
| 激进（约 60 Agent + 每组重复 3 次） | ~60 | 15 | ¥0.8–1.5 | **¥5–9** ⚠️ |

**结论**：

- 单轮跑完六组（不重复），预算 ¥5 **大概率够用**；
- 但「完整种子 + 每组重复 3 次」的稳健设计**会大概率超 ¥5**，需追加预算或降低重复次数；
- 建议策略：先用 1 次中等规模（~30 Agent × 15 轮）实测单组成本，再倒推能否重复。

> ⚠️ 估算不确定性说明：Agent 数由 Zep 图谱实体数决定（`max_agents_allowed = 实体数 × 0.9`），
> LLM 生成结果每次不同，成本无法在跑前精确锁定。**必须以首组实测值修正后续估算。**

## 五、未达标项与限制（如实记录）

### 5.1 Agent 数量未达目标（5 个 vs 实际 3 个）

**原因**：Agent 数量**不能由用户直接设定**，而是：
`实体数（Zep 从种子文本中抽取） × 0.9`，且受 `agents_per_hour_min/max`（本次 = 1~2）约束。

本次使用微种子（1364 字符，刻意压缩），导致：
-ontology 仅识别出 `Organization` / `Person` 两类；
- 实体过少 → 仅 3 个 Agent，且**全部是机构/当事人，没有普通公众 Agent**。

**解决方向**（供正式实验决策）：

1. 使用完整种子 `seed_main_baihaitun.md`（11227 字符，实体显著更多）；
2. 在 `simulation_requirement` 中显式要求"必须包含普通网民/社区长辈/青年学生等至少 N 类公众角色"；
3. 若上游仍不足，可直接改写 `simulation_config.json` 的 `agent_configs` 后手动启动（需验证可行性）。

### 5.2 互动数据几乎为零

本次产出 **全部是发帖动作**，无点赞/转发/评论，`num_likes` 等全为 0。

**原因**：3 个 Agent 规模下，OASIS 的推荐/互动机制几乎不触发。

**含义**：当前数据**可以进行**简单的逐轮传播量分析，
但**不能**计算转评率、二级传播、网络级联等指标。放大 Agent 规模后再评估。

### 5.3 尚未启动的实验

按指令要求，**本次未开展**任何正式六组实验。相关实验组目录均不存在，
`plot_fig_4_1_4_2.py` 已加守卫拒绝出空图。
