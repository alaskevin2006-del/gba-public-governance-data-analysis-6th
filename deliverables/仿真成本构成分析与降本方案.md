# 仿真 LLM 成本构成分析

> 分析对象：单次正式运行（8 Agent × 16 轮，Reddit 单平台，seed 20261022，deepseek-chat）
> 数据来源：`E1A_rep3/process_stdout.txt` 原始日志反推 + CAMEL/OASIS 源码核对
> 日期：2026-10-21

## 1. 结论先行

**贵的不是"调用次数"，是"每次调用携带的上下文"。**

直觉上的估算方式是：8 Agent × 16 轮 = 128 次决策，每次几百 token → 几万 token → 几毛钱。
真实情况是：**128 次决策 × 每次携带约 5–6 万 tokens 的完整上下文 → 单次运行千万级 input tokens。**

差额约 **200–300 倍**。根因是三层结构性浪费（第 3 节），而非模型定价。

## 2. 证据链

### 2.1 上下文窗口上限 = 64,000（实测）

```python
ModelType('deepseek-chat').token_limit  # = 64000
```

### 2.2 日志反推：每次调用的上下文已经顶到窗口上限

`camel/agents/chat_agent.py:899` 在写入记忆前会检查剩余预算并打印 WARNING。用 `64000 − remaining_budget` 即可反推当时的上下文规模。对 `E1A_rep3` 的 141 条切片事件：

| 指标 | 值 |
|---|---|
| 上下文 tokens 最小 / **中位** / 最大 | 55,009 / **63,996** / **64,000** |
| 上下文 > 60,000 的事件占比 | **93%** |
| 单次写入消息的 tokens（最小/中位/最大） | 7 / 673 / **15,295** |
| >1000 tokens 的大消息条数 / 合计 | 63 条 / 596,831 tokens |

**这份日志直接说明：从中后段开始，每个 Agent 的上下文都顶到了 64,000 的窗口上限，一轮不落地以满窗口发送。**

### 2.3 但平台的真实信息量只有 7.5 KB

对同一次运行统计 `CREATE_POST` + `CREATE_COMMENT` 的全部正文：

| 项目 | 值 |
|---|---|
| 16 轮累计内容条数 | 62 条 |
| 累计正文字节数 | **7,701 字符 ≈ 7.5 KB** |

**7.5 KB 的正文，撑起了 64,000 tokens（约 10 万字符以上）的上下文。两者相差一个数量级以上。**

### 2.4 源码：每轮把全平台帖子的完整 JSON 原样塞进 prompt

`oasis/social_agent/agent.py:124`：

```python
async def perform_action_by_llm(self):
    env_prompt = await self.env.to_text_prompt()          # ← 全平台观察
    user_msg = BaseMessage.make_user_message(
        role_name="User",
        content=(f"Please perform social media actions after observing the "
                 f"platform environments. ... "
                 f"Here is your social media environment: {env_prompt}"))
    response = await self.astep(user_msg)
```

`oasis/social_agent/agent_environment.py:58`：

```python
posts_env = json.dumps(posts["posts"], indent=4)   # ← indent=4 + 全量
```

每条帖子不只正文，还带 `post_id / agent_id / created_at / num_likes / num_dislikes / comments[]` 等元数据，且**每轮重发全量**（不是增量）。

### 2.5 源码：一次决策 ≥ 2 次调用，第 2 次上下文更大

`camel/agents/chat_agent.py:1992` 的 `while True` 循环：

```python
while True:
    openai_messages, num_tokens = self.memory.get_context()   # 重拉全量上下文
    response = await self._aget_model_response(openai_messages, ...)  # 第 i 次调用
    ...
```

带 tools schema 时第 1 次返回 tool_call → 执行 → 第 2 次再走一遍 `get_context()` 重新发送（此时上下文已因 tool result 变大）→ 生成最终文本才退出。**所以每个 agent-step 至少 2 次付费调用。**

## 3. 三处结构性浪费

| # | 浪费 | 机制 | 后果 |
|---|---|---|---|
| **A** | **JSON 序列化膨胀** | `json.dumps(..., indent=4)` 且携带全部元数据；正文 ~50 字/条被包装成 ~300–400 字符/条 | 单条 env_prompt 达 **10,000–15,295 tokens**（日志实测），而正文只有几十字 |
| **B** | **全量重发而非增量** | 每轮每个 Agent 都重新拉取平台上所有帖子的完整 JSON，不看上一轮已看过什么 | 第 k 轮的 env_prompt 与第 k−1 轮高度重叠 |
| **C** | **记忆零裁剪 → O(n²)** | `token_limit=64000` 上限极高，CAMEL 的裁剪/摘要机制在整个 16 轮内**从未触发**；历史全额重发 | 第 k 轮 input ≈ Σ(前 k 轮全部内容)，总消耗随轮次**平方增长** |

三者叠加：**A × B 让单次 prompt 变大，C 让这些大 prompt 被反复重发。**

## 4. 成本账（估算，非实测）

DeepSeek-chat 公开计价：输入命中缓存 ¥0.5/M、输入未命中 ¥2/M、输出 ¥8/M。

| 项 | 取值 |
|---|---|
| agent-step 数 | 8 Agent × 16 轮 = 128 |
| 每次 step 的调用次数 | ≥ 2（见 2.5） |
| 付费调用总数 | **≥ 256** |
| 平均 input tokens/次 | 约 40,000–45,000（前期小，后期 64,000 顶格） |
| 总 input tokens | **约 1,000 万 – 1,150 万** |
| 输出 tokens | 约 5 万 → ¥0.4 |
| 理论成本（缓存命中 70%） | **约 ¥10–11** |
| 理论成本（缓存命中 90%） | **约 ¥7.5** |
| **实测单次成本** | **约 ¥4–5** |

理论与实测差约 2 倍，可能来自：部分 step 只有 1 次调用、DeepSeek 前缀缓存命中率高于估计、实际中间轮次上下文未全程顶格。**但量级完全吻合：单次运行千万级 input tokens。**

> 严格账单无法离线还原——运行设法把 `prompt_tokens/completion_tokens` 打进日志。
> 若要精确对账，需在 `camel/models/base_model.py` 的实际返回处加一行 usage 累加（约 10 行），代价是一次额外运行。

## 5. 降本方案与对应风险

| 方案 | 改动位置 | 预估降幅 | **对实验有效性的风险** |
|---|---|---|---|
| **① 去掉 JSON 缩进** | `agent_environment.py:58` 去掉 `indent=4` | 单条 prompt −20~30% | 低（信息等价），但**Agent 看到的格式变了** |
| **② 精简帖子字段** | 只回传 `post_id / content / num_likes`，去掉冗余元数据 | 再 −30~40% | 中（若某些字段被 Agent 用于决策，可能改变行为） |
| **③ 限制一次可见帖子数** | `get_posts_env()` 里截断到最近 N 条 | 后期轮次 −50%+ | **高**：等于改了 Agent 的信息环境 |
| **④ 记忆裁剪 / 定期摘要** | 为 ChatAgent 指定较小的 `token_limit`，或每 N 轮压缩历史 | **最大**：O(n²) → 约 O(n)，总账可降至 1/3–1/5 | **高**：直接改变 Agent 的记忆可得性 |
| **⑤ 减少 step 内调用次数** | 让 tool_call 后不再生成总结 | −50% 调用数 | 中 |
| **⑥ 缩短轮次 / 减少 Agent** | 仿真参数 | 线性下降 | **高**：等价于换实验条件 |

### ⚠️ 关键提醒：降本 ≠ 白拿

**上述任何一项改动，只要改变了 Agent 实际看到的 token，就等于修改了实验条件。**

- ①②③④ 都会改变 Agent 的决策输入，**改后跑出的数据不能与现有六条件数据混为一组**；
- 若要采用，必须在**新配置下把所有条件和所有重复全部重跑**，并重新做组间可比性论证；
- 唯一**完全安全**的降本手段是 ⑥——但它降低的是样本信息量，不是效率。

因此建议：**除非预算不足以完成基本重复，否则本期不要在已有数据流里混用新配置。**

## 6. 对本申报项目的含义

1. **¥4–5/次 × 6 条件 × 3 次重复 = ¥72–90**，这是当前配置下把重复补齐的真实代价（此前按"¥1–2/次"估算是错的，根源是 DeepSeek 延迟入账造成的读数假象）。
2. **优先做 Agent 构成扩充，而不是先补重复**：8 个 Agent 中 5 个官方账号造成的地板效应是阴性结果的主因；即便提高重复次数也难以产生可检出的组间差异。而扩充 Agent 会进一步线性推高成本（人数 × 0.9 → 更多 step）。
3. **若必须控预算**，建议顺序：
   - 先做 ①+②（纯序列化优化，信息几乎等价，降幅 40–55%，风险相对最低）；
   - 在新配置下重跑**全部**六条件，接受成本约 ¥35–45；
   - ④（记忆裁剪）作为最后手段，因为它对 Agent 行为影响最大，需要额外的效度论证。
